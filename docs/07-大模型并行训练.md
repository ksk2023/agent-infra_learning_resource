# 第 07 章：大模型并行训练

## 本章导学

并行策略不是菜单上的互斥选项，而是围绕“模型是否放得下、batch 是否足够、通信是否划算、设备拓扑如何”组合出的方案。

## 学习目标

- 区分 DP、FSDP/ZeRO、TP、PP、EP 与序列/上下文并行。
- 从状态、激活和通信三个维度比较方案。
- 读懂一种训练框架的并行配置。
- 为给定模型与集群提出可验证的并行设计。

## 1. Data Parallel 与状态分片

### DDP

每个 rank 通常保留完整参数、梯度和优化器状态，切分数据并同步梯度。实现相对直接，但模型状态必须能在单卡容纳。

### ZeRO

- ZeRO-1：分片优化器状态。
- ZeRO-2：进一步分片梯度。
- ZeRO-3：进一步分片参数。

### FSDP

FSDP 将参数、梯度和优化器状态分片，并在需要时通过集合通信汇聚参数用于计算。它减少单卡状态冗余，但引入 AllGather/ReduceScatter 等通信和更复杂的内存生命周期。

选择时要问：峰值显存发生在常驻状态、临时汇聚的参数、激活，还是通信 workspace？

## 2. Tensor Parallel（TP）

TP 将矩阵乘等计算沿列或行切到多个设备：

- column parallel：切输出维度，后续可能需要汇聚。
- row parallel：切输入维度，部分结果需要归约。
- attention/MLP 的切分要与 head、hidden 维度和模型结构对齐。

特点：

- 能降低单层计算与部分参数的单卡负担。
- 在层内频繁通信，通常更依赖高速设备互联。
- TP 度数受可整除性、并行效率和拓扑限制。

## 3. Pipeline Parallel（PP）

PP 将不同层放在不同 stage：

```text
micro-batch 1 -> stage 0 -> stage 1 -> stage 2
micro-batch 2 ->          stage 0 -> stage 1
micro-batch 3 ->                     stage 0
```

micro-batch 让流水阶段重叠，但仍有 pipeline bubble。需关注：

- stage 间激活传输。
- 各 stage 负载均衡。
- micro-batch 数与 bubble。
- 激活显存和调度方式（不同调度会改变峰值）。

PP 的通信频率与 TP 不同，但不能简单断言“PP 总是更省网络”。

## 4. Expert Parallel（EP）与 MoE

MoE 中每个 token 只激活部分专家。EP 将专家放到不同设备，token 常需通过 AllToAll 路由到对应专家，再返回。

核心系统问题：

- 专家负载是否均衡。
- 路由是否造成通信热点。
- 容量因子、丢弃/溢出策略如何影响质量与吞吐。
- 总参数、激活参数和每 token FLOPs 不能混用。

## 5. 序列/上下文并行

当序列很长时，仅分片参数还不够，激活和 attention/序列维计算也可能成为瓶颈。不同框架对 sequence parallel、context parallel 的命名和切分范围可能不同，阅读时应明确：切的是哪几个算子、哪些激活、通信发生在哪里。

## 6. 如何选择：先做约束表

| 约束 | 优先检查 |
|---|---|
| 单卡放不下优化器状态 | ZeRO/FSDP 等状态分片 |
| 单层权重或计算难以单卡承担 | TP，结合节点内高速互联 |
| 层数很多且可拆 stage | PP，评估 bubble 与负载 |
| MoE 专家无法集中放置 | EP，重点测 AllToAll 与均衡 |
| 长序列激活过高 | 序列/上下文并行、checkpoint、attention backend |
| 数据并行不足、全局 batch 固定 | 联合调整 DP 与 accumulation |

最终组合通常写成 `DP × TP × PP × ... = world_size`，但具体维度和实现以框架文档为准。

## 7. 最低实践：并行方案评审

选择一个假想模型与集群，写一页设计：

1. 参数、梯度、优化器和激活的显存预算。
2. DP/FSDP/TP/PP/EP 各维度的大小与原因。
3. 每种通信发生在何处、数据量级如何。
4. 一个最可能瓶颈和一个备选方案。
5. 从单节点到多节点的三组实验，每次只改一个维度。

可使用 `code/ch05/memory_estimator.py` 和 `code/ch06/ring_allreduce.py` 做第一版量级估算，但不要将理想模型当作最终实测。

## 8. 源码阅读路线

按“教育实现到生产实现”顺序：

1. [huggingface/picotron](https://github.com/huggingface/picotron)：面向教学的精简多维并行实现。
2. [huggingface/nanotron](https://github.com/huggingface/nanotron)：对照较完整的训练实现。
3. [pytorch/torchtitan](https://github.com/pytorch/torchtitan)：PyTorch 原生的大模型训练组合与可组合性。
4. [NVIDIA/Megatron-LM](https://github.com/NVIDIA/Megatron-LM)：围绕一个具体问题阅读 TP/PP/MoE，而不是无目标通读。
5. [deepspeedai/DeepSpeed](https://github.com/deepspeedai/DeepSpeed) 与 [hpcaitech/ColossalAI](https://github.com/hpcaitech/ColossalAI)：比较 ZeRO、并行和运行时抽象。

## 9. 本章自测

1. FSDP 为什么能减少常驻显存却仍可能出现瞬时峰值？
2. 为什么 TP 通常更在意节点内高速互联？
3. 增加 micro-batch 数对 PP 一定只有好处吗？
4. MoE 的总参数量能否直接代表每 token 计算量？

<details><summary>参考思路</summary>

1. 计算时需要汇聚参数，激活、临时 buffer 和通信空间也仍占显存。
2. 层内切分会产生较频繁通信，慢互联容易成为瓶颈。
3. 不是，调度、激活驻留、micro-batch 变小后的 kernel 效率都需权衡。
4. 不能，路由只激活部分专家，应区分总参数与激活参数。
</details>
