# 第 01 章：AI Infra 全景

## 本章导学

模型只定义“算什么”，AI Infra 决定它“在哪里、以什么资源、多快、多可靠地算”。本章先建立全栈地图，之后每章都能回到这张地图定位。

## 学习目标

- 区分模型、框架、运行时、硬件与平台层。
- 画出训练和在线推理的端到端数据流。
- 用质量、延迟、吞吐、成本和可靠性描述系统目标。
- 理解局部优化为什么可能损害全局目标。

## 1. 一张全栈地图

```text
应用：搜索 / 对话 / 推荐 / Agent / 多模态
                  |
模型工程：模型定义 / 微调 / 对齐 / 评测
                  |
训练与推理系统：训练器 / 并行策略 / 推理引擎 / Serving
                  |
运行时与编译：PyTorch / JAX / CUDA / Triton / 算子库
                  |
资源层：CPU / GPU / NPU / HBM / RDMA / 存储 / 网络
                  |
平台层：容器 / Kubernetes / 调度 / 弹性 / 权限 / 多租户
                  |
贯穿层：数据版本 / 实验追踪 / 监控 / SLO / 安全 / 成本
```

边界不是绝对的。例如 vLLM 同时涉及模型执行、KV 管理和 serving；Kubernetes 本身不懂训练语义，需要 JobSet、Kubeflow Trainer 等补充。

## 2. 一次训练任务的生命周期

```text
代码与配置
  -> 数据读取、解码、清洗、分词
  -> 批次组装与设备传输
  -> 前向计算
  -> 反向传播
  -> 梯度通信与同步
  -> 优化器更新
  -> 指标、评测、checkpoint
  -> 故障恢复或下一轮
```

分析时要同时看四条流：

1. **数据流**：样本、token、标签如何移动。
2. **计算流**：算子在哪些设备执行。
3. **状态流**：参数、梯度、优化器状态、KV 或 checkpoint 存在哪里。
4. **控制流**：谁启动、调度、同步、失败重试和回收资源。

只看 GPU 利用率会漏掉数据等待、通信、CPU 预处理和 checkpoint 停顿。

## 3. 一次在线推理的生命周期

```text
客户端
  -> 网关、鉴权、限流
  -> 路由与排队
  -> tokenizer
  -> scheduler 组批
  -> prefill：处理输入并生成 KV
  -> decode：逐 token 生成
  -> 流式返回、取消与资源释放
  -> 日志、指标、trace、成本归因
```

关键区别：训练通常追求固定计算图下的高利用率和可恢复性；在线 serving 面对变长请求、并发、尾延迟和持续到达，调度与内存管理会成为核心。

## 4. 五个互相制约的目标

| 目标 | 常见指标 | 误区 |
|---|---|---|
| 质量 | 任务准确率、回归测试、安全指标 | 只看速度，不看精度回归 |
| 延迟 | TTFT、TPOT、E2E、P99 | 只报平均延迟 |
| 吞吐 | tokens/s、requests/s、samples/s | 用超大 batch 的数字代表在线体验 |
| 成本 | 每百万 token 成本、GPU 小时、存储与网络成本 | 只算 GPU 单价，不算空闲和失败 |
| 可靠性 | 成功率、SLO、恢复时间、故障范围 | 把进程存活等同于服务健康 |

“更快”必须说明是哪一种指标、哪种负载、哪个分位数和什么质量约束。

## 5. 一个优化如何沿栈传播

以 FP8 为例：

- 模型层：需要验证数值稳定与任务质量。
- kernel 层：必须有适配的低精度实现才有收益。
- 硬件层：不同架构的低精度能力不同。
- serving 层：显存下降可能允许更大 batch，也可能改变调度行为。
- 平台层：模型制品、配置、评测和回滚都要同步管理。

因此，不能仅凭“精度位数减半”就承诺端到端加速减半。

## 7. 本章自测

1. GPU 利用率接近 100% 是否一定意味着端到端吞吐达到最优？
2. 为什么增大 batch 可能提高吞吐却损害在线体验？
3. checkpoint 属于数据流、状态流还是控制流？
4. 为什么“引擎进程还在”不能证明服务健康？

<details><summary>参考思路</summary>

1. 不一定，可能存在低效 kernel、无意义重复计算或下游瓶颈，且利用率不能说明有效工作量。
2. 排队和单步计算时间可能增加，TTFT/TPOT 与尾延迟可能恶化。
3. 主要是状态流，保存/恢复动作由控制流触发，持久化又涉及数据流。
4. 进程可能存活但无法调度新请求、模型加载失败或持续返回错误。
</details>
