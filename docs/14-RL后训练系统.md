# 第 14 章：RL 后训练系统（选修）

## 本章导学

RL 后训练把推理 rollout、奖励/环境、训练更新和权重同步放进一个循环。它既是训练问题，也是在线生成、分布式调度和数据一致性问题。

## 学习目标

- 画出 actor/learner、rollout、reward 与权重同步的系统图。
- 理解同步与异步 RL 的吞吐、样本陈旧和资源利用取舍。
- 识别训练—推理引擎不一致与权重更新开销。
- 阅读一个 RL 框架的关键调用链。

## 1. 一个典型循环

```text
当前策略权重
  -> rollout 引擎生成轨迹
  -> 环境/奖励模型/验证器打分
  -> 优势估计与经验组织
  -> learner 计算梯度并更新
  -> 新权重同步回 rollout
  -> 下一轮
```

不同算法可能还需要 reference model、critic、value state、KL 约束或多种环境。系统图中要区分模型副本、 optimizer 状态、轨迹数据和版本号。

## 2. 为什么会有多种执行引擎

Rollout 重视高并发生成、KV Cache 和采样；训练重视反向、优化器状态和并行分片。两者可能采用不同：

- kernel 与数值路径。
- 并行切分与 dtype。
- batch/sequence 组织。
- tokenizer、采样和停止逻辑。

因此，“同一份权重”不自动保证训练与生成数值语义完全一致。需要用固定输入比较 logits、采样配置、特殊 token、chat template 和停止条件。

## 3. 同步与异步

### 同步

等当前批次 rollout 完成后训练，再统一更新权重。版本关系清楚，但生成长度不均或环境慢时会形成等待。

### 异步

Rollout 与 learner 重叠执行，提高资源利用，却引入：

- 策略版本陈旧（off-policy/staleness）。
- 队列和背压。
- 样本丢弃或重要性修正策略。
- 权重同步与正在运行请求的协调。
- 更难复现的执行顺序。

异步不是纯性能开关，它会改变算法语义和实验解释。

## 4. 资源利用与数据偏斜

Rollout 的序列长度、工具调用次数和环境延迟差异很大。要监控：

- 每阶段等待时间与设备空闲。
- 轨迹长度分布和长尾。
- learner/rollout 的产能比。
- 权重同步时间与大小。
- 队列年龄、策略版本分布与丢弃率。
- reward/verifier 的吞吐和失败。

单纯增加 rollout worker 可能让经验队列膨胀、陈旧加剧，而不是提高有效学习速度。

## 5. 权重同步与状态一致性

需要回答：

1. 训练分片格式如何转换成推理引擎布局？
2. 同步期间旧请求继续使用哪个版本？
3. 部分 worker 更新失败怎么办？
4. 权重、tokenizer、配置和采样参数是否作为同一版本发布？
5. 如何回滚到上一份健康权重？

将权重同步设计成有版本、有确认、有失败处理的过程，不要只把它看作一次文件复制。

## 6. Agentic RL 的额外边界

当 rollout 调用工具和环境时，还需考虑：

- 沙箱、凭证最小权限与网络隔离。
- 环境重置与可复现性。
- 工具超时、重试与幂等。
- 长轨迹存储、敏感数据与审计。
- 非确定性环境下奖励和轨迹的比较。

这类系统实验应使用自有的隔离测试环境，不给 agent 无边界生产权限。

## 7. 最低实践：画时序图

画同步与异步两张时序图，包含 rollout、reward、learner、权重同步和队列。标注：

- 哪些阶段可重叠。
- 每条轨迹对应的 policy version。
- 哪些等待会形成 bubble。
- 哪个指标能发现样本过旧或资源闲置。

再写一次故障推演：learner 失败、rollout 失败、reward 超时和权重同步部分成功分别如何处理。

## 8. 源码阅读路线

- [huggingface/trl](https://github.com/huggingface/trl)：从较上层的 Transformer 后训练接口理解算法与训练配置。
- [verl-project/verl](https://github.com/verl-project/verl)：围绕 HybridFlow、rollout/learner 和资源映射阅读。
- [OpenRLHF/OpenRLHF](https://github.com/OpenRLHF/OpenRLHF)：观察 Ray、推理引擎与训练组件的组合。
- [THUDM/slime](https://github.com/THUDM/slime)：学习 RL scaling 与训练—推理协同。
- [NVIDIA-NeMo/RL](https://github.com/NVIDIA-NeMo/RL)：对照可扩展后训练工具链。
- [ray-project/ray](https://github.com/ray-project/ray)：补分布式 task、actor、对象与资源调度基础。

## 9. 本章自测

1. 为什么异步 rollout 会改变算法语义？
2. 为什么 rollout 与训练使用同一权重文件仍可能数值行为不同？
3. 为什么生成速度提高不一定提高有效学习吞吐？
4. 权重同步为什么需要版本与确认协议？

<details><summary>参考思路</summary>

1. 轨迹可能由旧策略产生，引入 off-policy、陈旧和修正/丢弃问题。
2. kernel、dtype、并行、模板、采样和停止逻辑可能不同。
3. 队列可能堆积、样本陈旧、learner 成为瓶颈，或奖励质量下降。
4. 多 worker 需要知道可用版本、处理部分失败与回滚，避免混用不一致状态。
