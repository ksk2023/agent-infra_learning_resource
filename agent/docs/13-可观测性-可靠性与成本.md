# 第 13 章：可观测性、可靠性与成本

## 本章导学

Agent 出错时，只保存最终答案无法判断是模型、检索、工具、权限、排队还是状态恢复出了问题。本章建立从 run trace 到 SLO 与单位成功成本的工程闭环。

## 学习目标

- 为 run、model、tool、retrieval 和 approval 设计 trace 层级。
- 使用 metrics、logs、traces 和任务评测协同诊断。
- 设计超时、退避、熔断、降级、取消和恢复策略。
- 计算满足质量、安全与 SLO 的单位成功成本。

## 1. 一条有用的 Trace

```text
invoke_agent / run
  ├─ context_build
  ├─ model_call
  ├─ tool_call: search
  │    └─ retrieval / upstream HTTP
  ├─ model_call
  ├─ approval_wait
  ├─ tool_call: create_ticket
  └─ verifier / final_response
```

每个 span 至少关联 `run_id`、起止时间、状态、错误类别和版本；model span 可记录模型与 token 用量，tool span 可记录工具名和调用关联。`user_id`、完整 prompt、文档正文等敏感或高基数字段不应无控制进入指标标签和日志。

## 2. Metrics、Logs、Traces 与 Evals

- **Metrics**：成功率、在途 run、队列、P95/P99、token、工具错误、审批等待、成本趋势。
- **Logs**：离散状态迁移与结构化错误，控制敏感信息和采样。
- **Traces**：单次任务跨模型、工具、检索与人工阶段的时间和因果关系。
- **Evals**：固定任务上的质量、安全和可靠性结论，不由线上延迟指标替代。

排查顺序：

```text
SLO/质量告警 -> 按版本、工具、任务类型缩小范围
  -> 看队列、错误、预算和资源指标
  -> 用 trace 定位具体阶段
  -> 用受控日志/回放复现
  -> 加入回归任务集
```

## 3. 可靠性模式要匹配语义

| 模式 | 适用 | 误用风险 |
|---|---|---|
| 超时 | 所有模型、工具、排队与审批阶段 | 只取消本地等待，未取消上游副作用 |
| 指数退避 + jitter | 明确暂时性、幂等失败 | 对权限拒绝和参数错误重试 |
| 熔断 | 上游持续故障 | 没有恢复探测或影响全部租户 |
| 降级 | 可用只读答案替代写动作 | 降级结果冒充完整任务成功 |
| 幂等/状态查询 | 写工具重试与恢复 | 仅客户端假设幂等，服务端无约束 |
| 取消 | 用户撤销、超时、预算耗尽 | 忽略已提交动作的补偿和审计 |

失败时应返回真实状态：`completed`、`partially_completed`、`waiting`、`failed` 和 `cancelled` 不能混为“成功响应”。

## 4. Agent SLO

普通 HTTP 成功率不足以描述 Agent。可定义：

```text
在指定任务与流量分布下，一个月内：
- 至少 X% 的可评测任务通过最终状态验证且无政策违规；
- 成功任务的端到端 P95 低于某阈值；
- 高风险写动作 100% 经过规定授权/审批；
- 每个成功任务成本不超过预算。
```

SLO 必须写明测量窗口、任务范围、无效样本、人工等待是否计入、环境故障与评分器故障如何处理。不可完成任务和拒答是否算成功，要按任务目标预先定义。

## 5. 成本模型

```text
总成本 = 模型输入/输出 + 工具/API + 检索/存储
       + 沙箱/计算 + 网络 + 运维 + 人工审批 + 失败/重试

单位成功成本 = 总成本 / 满足质量、安全和 SLO 的任务数
```

多 Agent 和反思常同时增加模型调用与延迟。缓存、摘要和较小模型可能降低成本，但必须通过同一任务集确认没有损害质量和安全。

## 6. 最低实践：生成一份运行摘要

运行：

```bash
python code/ch13/trace_metrics.py
```

完成：

1. 汇总多次 run 的成功率、延迟分位数、模型调用、工具错误和估算成本。
2. 将失败但延迟很短的 run 加入数据，解释为何低平均延迟不等于更好。
3. 计算单位成功成本，并观察失败重试如何影响它。
4. 为一个“工具超时增加”的告警写 runbook：影响、排查入口、缓解、回滚。
5. 检查 trace 字段，移除密钥、完整个人信息和无界高基数标签。

### 验收标准

能从聚合指标回到具体 run 证据；成本只把满足质量与安全条件的任务计为成功。

## 7. 生产实践

建立用户面、Agent 面、资源面三层面板，并演练一次模型故障、一次工具超时、一次卡住的人工审批和一次恢复。灰度发布绑定模型、prompt、工具 schema、运行时与评分器版本，保留回滚路径。

## 8. 本章自测

1. HTTP 200 且响应很快，为什么仍可能是 Agent 失败？
2. 为什么完整 prompt 不宜默认写入所有 trace？
3. 为什么单位成功成本通常比每 token 成本更有业务意义？
4. 权限拒绝为什么不能通过重试解决？

<details><summary>参考思路</summary>

1. 响应可能声称完成、只有部分完成或未通过验证；传输成功不等于任务成功。
2. 可能含隐私、密钥和不可信内容，还会增加存储与访问风险；需最小化和受控采样。
3. 它包含失败、重试、工具和人工成本，并以真实有效产出为分母。
4. 权限拒绝是确定性授权结果，重试不会合法改变权限，还可能形成绕过尝试。
</details>
