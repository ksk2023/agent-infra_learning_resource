# 第 04 章：工具设计与函数调用

## 本章导学

Agent 的能力上限常由工具接口而非提示词决定。模糊描述、过大权限、无结构错误和不可控输出会让强模型也不可靠。本章把工具当作有契约、有身份、有生命周期的系统接口来设计。

## 学习目标

- 设计名称、描述、输入输出 schema 和错误结构。
- 区分数据工具、动作工具和编排工具。
- 处理超时、重试、幂等、权限和结果截断。
- 为工具建立独立测试，不依赖模型“碰巧调用正确”。

## 1. 三类工具

| 类型 | 示例 | 主要要求 |
|---|---|---|
| Data | 搜索、读文档、查订单、获取指标 | 数据范围、来源、时效、权限、引用 |
| Action | 创建工单、发邮件、修改记录、执行代码 | 授权、幂等、审批、审计、撤销/补偿 |
| Orchestration | 调用专家 Agent、启动子任务 | 输入输出契约、预算、状态归属、循环控制 |

同一个工具可同时涉及多类，但必须显式说明副作用。例如“查询并自动关闭重复工单”不是只读查询。

## 2. 工具契约清单

一个生产候选工具至少回答：

```text
名称：模型和其他工具是否容易区分？
描述：何时使用、何时不用、需要什么前置信息？
输入：类型、必填项、范围、枚举、资源标识是否明确？
输出：是否结构化、是否包含来源/时间/单位、最大多大？
错误：参数、权限、未找到、限流、超时、业务冲突如何区分？
副作用：读还是写，是否可逆，是否需要审批？
身份：以用户、服务账号还是租户身份执行？
可靠性：超时、重试、幂等键、取消和并发约束是什么？
```

工具描述帮助模型选择，但不是安全声明。`read_only: true` 之类的元数据也必须由可信执行方验证，不能仅由外部服务器自称。

## 3. 输入与输出设计

### 输入

- 优先资源 ID 和枚举，减少自由文本路径、URL、SQL 或 shell。
- 对金额、数量、时间范围和分页大小设置业务上限。
- 将 `confirm=true` 视为界面信息而非授权凭证；授权由运行时决定。
- 不要把密钥作为模型可见参数传入工具。

### 输出

- 返回任务需要的字段，而非整个上游响应。
- 对长列表分页，对大文本返回摘要加受控 artifact 引用。
- 保留来源、更新时间、单位和截断标记。
- 错误使用稳定代码；不要把敏感堆栈和内部连接串返回给模型。

“把更多原始数据塞给模型”既增加成本，也扩大提示注入与隐私暴露面。

## 4. 超时、重试与幂等

```text
调用前：生成 call_id；写操作生成 idempotency_key
执行中：设置连接/读取/总超时，响应取消
失败后：先判断错误类型与是否可能已提交
重试时：仅对明确可重试且幂等的操作使用退避
恢复后：用操作 ID 查询真实状态，避免重复写入
```

幂等不是“函数运行两次结果看起来差不多”，而是同一逻辑操作重复请求不会产生额外副作用。支付、发邮件、创建资源等通常需要服务端支持幂等键或唯一约束。

## 5. 工具注册表与工具选择

工具数量增加会带来描述 token、选择混淆和权限扩张。可采用：

1. 按用户身份和任务阶段只暴露必要工具。
2. 用确定性路由先缩小工具集合。
3. 对大量工具做可审计的检索/渐进发现，再加载详细 schema。
4. 将高风险写工具与低信任浏览上下文分离。

不要一开始就给 Agent 一个无限制 shell 来代替工具设计。专用接口更容易校验、测试和审计。

## 6. 最低实践：给一个工具写“合同”

阅读 `code/ch03/mini_agent.py` 中的计算器实现，然后新增一个 `lookup_order` 假工具：

- 输入只接受限定格式的订单 ID。
- 数据按模拟用户命名空间隔离。
- 输出包含订单状态和模拟更新时间，不返回其他用户字段。
- 未找到、无权限和格式错误使用不同错误代码。
- 为正常、越权、空结果和畸形输入写单元测试。

扩展任务：设计 `cancel_order` 的幂等与审批方案，但不要直接连接真实业务系统。

### 验收标准

工具在不运行模型的情况下也可完整测试；任何模型生成的额外参数都不会绕过授权。

## 7. 源码任务

选择一个成熟 Agent SDK，跟踪一个函数工具从定义到结果回传的链路：

```text
函数签名/docstring -> schema 生成 -> 模型可见描述
  -> 参数解析/校验 -> guardrail/审批 -> 实际函数
  -> 错误格式化 -> trace -> 结果写回会话
```

固定 commit/tag，记录哪些能力由 SDK 提供，哪些仍需应用自己实现。

## 8. 本章自测

1. 为什么“工具返回空字符串”不是足够好的错误协议？
2. 为什么模型提供 `user_id=admin` 不能改变实际执行身份？
3. 写操作超时后直接重试有什么风险？
4. 为什么高权限工具不应与不可信网页内容同时无边界暴露？

<details><summary>参考思路</summary>

1. 空字符串无法区分无数据、失败、截断和权限问题，模型也无法采取合理下一步。
2. 执行身份必须由可信会话和授权系统决定，模型参数只是待校验输入。
3. 第一次可能已执行，重试会重复产生副作用；需幂等或先查询状态。
4. 网页中的注入可能诱导调用高权限工具，形成数据外泄或越权动作。
</details>
