# 第 11 章：Agentic RL 与持续改进（选修）

## 本章导学

许多 Agent 问题可以通过工具、上下文、环境和控制流修复，不需要训练。只有当稳定的行为缺口在评测中反复出现，并且拥有高质量轨迹与奖励时，才值得进入 SFT 或 RL。本章建立从系统改进到模型改进的决策顺序。

## 学习目标

- 区分 prompt/harness 改进、轨迹 SFT 和在线/离线 RL。
- 设计可复放的交互环境、轨迹数据和结果奖励。
- 理解长轨迹信用分配、 reward hacking 与分布漂移。
- 建立训练前后同一任务集和系统指标的评估闭环。

## 1. 先判断问题在哪一层

| 失败现象 | 优先检查 | 不宜立即做什么 |
|---|---|---|
| 工具参数类型错误 | schema、原生 tool calling、解析器 | 直接收轨迹训练 |
| 检索不到证据 | 数据、索引、权限、查询和召回 | 让模型背更多答案 |
| 重复循环 | 停止条件、状态、预算、重复检测 | 只增加最大步数 |
| 权限违规 | 模型外授权、工具隔离、审批 | 只在提示词写“不允许” |
| 多步策略持续低效 | 任务能力、规划和信用分配 | 假定换框架即可解决 |

只有最后一类在系统修复后仍有稳定缺口时，模型训练才成为主要候选。

## 2. 三种改进方式

### Prompt / Harness

改变指令、工具、上下文、验证器和运行时。优点是迭代快、可回滚；缺点是每步仍需模型泛化，长系统提示可能增加成本。

### 轨迹 SFT

使用经筛选的高质量交互轨迹监督微调，让模型学习格式、工具选择和局部策略。关键是轨迹正确性与覆盖，而非简单收集所有成功日志。错误工具结果、权限边界和不可完成任务也应有合适监督信号。

### RL

在环境中根据结果或过程奖励优化策略。适合有可靠 reward、可重复交互和足够训练预算的场景。环境成本、rollout 吞吐、模型权重同步、长尾轨迹和安全约束都会成为系统问题。

## 3. 轨迹数据的最小结构

```text
task / environment_snapshot / initial_state
policy_model / prompt_version / tool_schema_version
每一步：结构化动作、观察、状态差异、时间、用量
终止原因 / 最终环境状态 / verifier_result
失败标签 / 人工修正（如有）/ 数据来源与许可证
```

不要只存“模型最终说成功”。训练数据必须能追溯到真实环境结果和评分器版本。敏感信息、密钥和未经授权数据需在采集前控制，而非事后依赖脱敏补救。

## 4. 奖励设计

优先级通常是：

1. **可执行结果**：测试通过、数据库状态正确、文件产物满足检查。
2. **业务约束**：无越权、无政策违反、必要审批完整。
3. **任务效率**：在质量达标后，对步骤、时间和成本做适度优化。
4. **过程偏好**：格式、可读性等辅助信号。

风险：

- 只奖励最终文本会鼓励“声称完成”。
- 只奖励步骤少会鼓励跳过验证。
- 评分器漏洞会导致 reward hacking。
- 稀疏结果奖励难以指出长轨迹中哪一步出错。
- 用同一模型生成任务、执行并评分，可能形成封闭自洽而非真实能力。

安全违规应作为硬约束或明确失败，不应被小幅效率奖励抵消。

## 5. Rollout 与训练系统

一个概念性闭环：

```text
任务采样 -> 多环境 rollout -> 工具/沙箱交互
  -> 轨迹与结果验证 -> 数据筛选/奖励计算
  -> 策略更新 -> 新权重同步到 rollout
  -> 固定回归集 + 新环境泛化评测
```

需记录环境版本、策略版本、模型权重和评分器版本。异步 rollout 可能使用不同策略版本，影响数据口径；长任务还会造成 worker 空闲和排队，需要系统测量。

无 GPU 时仍可完成环境、验证器和数据 schema，并用离线脚本模拟 rollout 控制逻辑，但不能据此宣称训练收益。

## 6. 最低实践：写一个可验证环境设计

选择“模拟订单客服”或“本地代码修复”之一，定义：

1. 初始状态、可用工具、合法动作和终止条件。
2. 不依赖最终文本的最终状态验证器。
3. 10 个正常任务、5 个边界任务、5 个对抗任务。
4. 结果奖励、政策硬约束和效率指标。
5. 数据 schema、环境快照和训练/测试隔离方式。
6. 一项可能的 reward hacking 及检测方法。

### 验收标准

另一位学习者能按文档重置环境并验证一条轨迹；训练任务与隐藏回归任务不能共享答案或未来状态。

## 7. 真实训练实践

先跑通小模型、小环境和少量轨迹的完整链路，再扩大规模。比较训练前后同一模型在固定任务集上的成功率、pass^k、违规率、延迟和成本，同时检查未见工具与新环境泛化。

## 8. 本章自测

1. 为什么工具 schema 错误通常不应优先用 RL 修复？
2. 成功轨迹很多，为什么仍需失败与边界数据？
3. 为什么“最终文本说已完成”不是可靠奖励？
4. 训练集成功率提高能否证明真实业务泛化？

<details><summary>参考思路</summary>

1. 这是确定性接口问题，代码和协议修复更直接、可验证且成本低。
2. 模型还需学习错误恢复、不可完成识别和安全边界；只学成功路径可能脆弱。
3. 文本可与真实环境状态不一致，且易被策略利用；应使用独立验证。
4. 不能，需要未见任务、环境变化、线上约束和安全回归。
