# 第 01 章：Agent 全景

## 本章导学

模型定义“如何根据上下文生成下一步”，Agent 系统决定“下一步能否执行、作用于什么环境、结果如何回到上下文、何时停止”。本章先建立全栈地图，之后每章都能回到这张图定位。

## 学习目标

- 区分 chatbot、workflow、单 Agent 和多 Agent。
- 画出一次 Agent 任务的数据流、状态流和控制流。
- 用任务成功、可靠性、效率、安全和成本描述系统目标。
- 判断一个场景是否应该使用 Agent。

## 1. 一张全栈地图

```text
入口层：Web / CLI / IM / API / 定时事件
                  |
编排与运行时：Agent Loop / Graph / Queue / Checkpoint / Scheduler
                  |
决策层：模型 / 指令 / 规划 / 路由 / 反思 / 结构化输出
                  |
能力层：工具 / RAG / Memory / Skills / 其他 Agent
                  |
环境层：文件 / 数据库 / 浏览器 / 业务 API / 代码沙箱 / 操作系统
                  |
贯穿层：身份权限 / 审批 / 评测 / Trace / SLO / 成本 / 审计
```

“框架”通常只覆盖其中一部分。一个能生成工具调用的模型不等于完整 Agent；一个能执行固定 DAG 的平台也不一定是模型自主决策的 Agent。

## 2. Chatbot、Workflow 与 Agent

| 形态 | 谁决定下一步 | 优势 | 主要风险/代价 |
|---|---|---|---|
| Chatbot | 用户逐轮推动 | 简单、低延迟、易控制 | 缺少环境行动与持续状态 |
| Workflow | 开发者预先写代码路径 | 可预测、易测试、易审计 | 对未知分支适应性有限 |
| Agent | 模型根据观察动态选择动作 | 适合开放、多步、难预先穷举的任务 | 非确定性、成本、权限与评估更复杂 |
| Multi-Agent | 多个执行单元按协议分工 | 上下文隔离、专业化、并行 | 协调开销、错误传播、更多状态与攻击面 |

这里的核心区别是**控制流由预定义代码还是模型动态决策主导**，不是界面里出现了几个角色。实际系统常把二者混合：确定性代码负责权限、支付和发布，模型负责理解、检索和选择候选动作。

## 3. 一次任务的生命周期

```text
接收目标与约束
  -> 建立会话、身份、预算和可用能力
  -> 观察环境/读取上下文
  -> 模型选择最终回答或工具动作
  -> 参数校验、授权、审批与执行
  -> 观察结果、更新状态和证据
  -> 成功/失败/等待人工/达到预算
  -> 输出、审计、评测和资源清理
```

同时看四条流：

1. **数据流**：用户输入、文档、工具结果和产物如何移动。
2. **状态流**：会话、计划、记忆、checkpoint 和外部业务状态存在哪里。
3. **控制流**：谁决定下一步，谁有权拒绝、重试、暂停和终止。
4. **信任流**：哪些内容来自用户、可信系统或不可信外部环境，权限是否随数据错误传播。

只看最终回答会漏掉副作用、越权、重复执行和恢复行为。

## 4. 六个互相制约的目标

| 目标 | 常见指标 | 误区 |
|---|---|---|
| 任务质量 | 最终状态成功率、正确性、引用支持率 | 只看文字流畅度 |
| 可靠性 | 重复运行成功率、pass^k、恢复率、违规率 | 用一次成功代表稳定 |
| 延迟 | 端到端 P50/P95/P99、等待人工时间 | 只报模型生成时间 |
| 效率 | 步数、token、工具调用、并行度 | 步数少但动作错误也算高效 |
| 成本 | 每个成功任务成本、人工复核成本 | 只算模型输入输出费用 |
| 安全 | 越权拦截率、泄露事件、审批覆盖率 | 靠一句“不要执行危险操作” |

“更智能”必须说明改善了哪项指标、在哪组任务、什么约束下，是否牺牲其他目标。

## 5. 什么时候不该用 Agent

优先选择普通脚本或 workflow 的情况：

- 输入、规则和分支都能清楚穷举。
- 错误代价高，且没有可验证反馈或可靠审批。
- 任务只需要一次模型总结、分类或翻译。
- 一个确定性工具已经能稳定完成。
- 无法定义成功标准，也无法构造测试环境。

适合引入 Agent 的信号是：任务包含开放输入、动态路径、多步工具使用和有价值的反馈信号，并且增加的成功率足以覆盖延迟、成本与风险。

## 6. 最低实践：画一套架构图

为“根据内部文档回答并创建工单”的场景画图，标注：

- 用户、网关、Agent Loop、检索、文档库、工单工具和审计的位置。
- 哪些步骤只读，哪些会产生外部副作用。
- 文档中的恶意指令在哪里被当作数据而非命令。
- 创建工单前需要什么身份、校验与审批。
- 任务成功、P95 延迟、成本和违规分别如何测量。

### 验收标准

箭头必须表示真实的数据或控制关系；每个有副作用的组件旁边写出权限、幂等与失败处理。

## 7. 本章自测

1. 一个系统有 planner、researcher、writer 三个角色，就一定是多 Agent 吗？
2. 为什么固定 workflow 往往比完全自主 Agent 更容易审计？
3. “任务成功但违反业务政策”应该算成功吗？
4. 为什么模型输出工具名称后，不能直接执行？

<details><summary>参考思路</summary>

1. 不一定，可能只是同一模型在固定 workflow 中多次调用；需要看执行单元、状态与控制关系。
2. 路径和权限更明确，分支可预先枚举，测试与审计范围更稳定。
3. 不应，业务政策与安全约束是成功定义的一部分。
4. 还需 schema 校验、身份授权、参数检查、风险分级，必要时人工审批。
</details>
