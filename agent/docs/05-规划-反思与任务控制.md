# 第 05 章：规划、反思与任务控制

## 本章导学

长任务不是把同一个提示词循环更多次。有效系统需要把目标、子任务、依赖、验证、预算和恢复状态显式化。本章从 DAG 与 Plan-and-Execute 入手，再讨论反思何时有用、何时只是昂贵的自我重复。

## 学习目标

- 将目标分解为有依赖和验收条件的任务图。
- 区分预设 workflow、动态规划与执行中重规划。
- 用外部反馈驱动反思，避免无依据的自我肯定。
- 为重试、跳过、人工介入和终止定义状态语义。

## 1. 从目标到任务图

一个可执行子任务至少包含：

```text
id：稳定标识
objective：可观察的目标，而非“思考一下”
inputs：明确输入和上游 artifact
tools/permissions：允许使用的能力
acceptance：如何检查完成
budget：步数、时间、token 或费用上限
on_failure：重试、重规划、等待人工或终止
```

依赖形成有向图。无依赖任务可并行，有依赖任务必须等待所需 artifact 通过验收。依赖图中存在环时，调度器应拒绝执行，而不是无限等待。

## 2. 三种控制方式

| 方式 | 路径来源 | 适合 | 注意事项 |
|---|---|---|---|
| 固定 workflow | 开发者预先定义 | 稳定业务流程 | 用代码处理关键分支，不滥用模型 |
| Plan-and-Execute | 模型先规划，执行器按图运行 | 子任务较稳定、需要总览 | 环境变化后要显式重规划 |
| 动态 Agent Loop | 模型每一步选择 | 高不确定、反馈密集任务 | 预算、漂移、权限与停止更困难 |

实际系统常组合：固定“检索—审阅—发布”主干，模型只动态规划检索子任务；发布动作始终由确定性策略门控制。

## 3. 计划状态不是聊天历史

聊天历史记录“说了什么”，计划状态记录“现在做到哪里”。建议单独保存：

```text
pending / ready / running / waiting_approval
succeeded / failed_retryable / failed_final / skipped / cancelled
```

每次状态迁移由运行时记录，包含输入版本、执行者、时间和证据。不要让模型仅靠自然语言自述把 `failed` 改成 `succeeded`。

并行执行时还要定义共享状态的写冲突：两个子任务能否修改同一文件、同一条业务记录或同一预算？若不能，使用锁、分区或串行化。

## 4. 反思需要反馈

有效反思闭环：

```text
执行轨迹 -> 独立评价信号 -> 定位可改变原因
  -> 形成下一次可执行调整 -> 有预算地重试 -> 回归验证
```

反馈可以是单元测试、环境状态检查、检索证据、业务规则或人工意见。模型自评可以提供假设，但不能自动成为真值。

无效模式包括：

- 不增加新信息，只让同一模型“再仔细检查”。
- 反思写成笼统道歉，没有改变工具、参数或计划。
- 无限制修修补补，最终成本和副作用超过收益。
- 为通过有缺陷的评分器而 reward hacking，而非完成真实目标。

## 5. 重规划的触发与边界

适合重规划的信号：必要工具不可用、关键假设被证伪、依赖产物未通过验收、新约束出现。不适合重规划的信号：仅因模型想尝试更有趣路径、已完成结果未读、重复追求满分。

重规划必须保留：

- 已确认事实与其来源。
- 已完成副作用及不可重复动作。
- 已消耗预算。
- 原计划的失败原因。

“重新生成一份计划”不能重置真实世界状态。

## 6. 最低实践：构造并破坏任务 DAG

运行：

```bash
python code/ch05/dag_planner.py
```

完成：

1. 输出合法 DAG 的拓扑执行批次，确认同批任务无相互依赖。
2. 添加一个环，验证规划器拒绝执行。
3. 添加不存在的依赖和重复任务 ID，验证输入校验。
4. 为一个任务写 `acceptance`，描述失败时是否允许重规划。
5. 画出两个并行写同一文件的任务如何被改为串行或分区。

### 验收标准

拓扑排序只解决执行顺序，不证明任务语义正确；报告需明确这一边界。

## 7. 真实模型实践

选 20 个多步研究任务，对比：

- 直接 ReAct。
- 先生成 DAG，再执行。
- DAG + 一次有外部证据的重规划。

除成功率外，记录总步骤、重复检索、无效反思、token、延迟和计划过期次数。若更复杂方法只在少数任务有帮助，应报告分布而非只展示最佳案例。

## 8. 本章自测

1. 为什么任务依赖图不应只存在模型的自然语言计划里？
2. 有向无环图是否保证每个子任务都能成功？
3. 为什么“让模型反思五次”可能降低系统质量？
4. 重规划时为什么不能清零已消耗预算？

<details><summary>参考思路</summary>

1. 运行时需可机读地调度、校验、恢复和审计，自然语言难以可靠维持状态。
2. 不保证，DAG 只表达依赖且无环；工具、模型、输入和验收仍可能失败。
3. 没有新反馈时可能重复偏见、放大错误、增加成本并引入过度修改。
4. 真实资源和副作用已发生，清零会绕过限制并破坏审计。
</details>
