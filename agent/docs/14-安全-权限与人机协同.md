# 第 14 章：安全、权限与人机协同

## 本章导学

Agent 将语言理解连接到真实工具和 data，因此传统应用安全、提示注入和过度自主性会叠加。安全不能靠系统提示词单独实现；需要模型外的身份、授权、隔离、审批和审计。

## 学习目标

- 建立覆盖输入、检索、工具、记忆、协议和多 Agent 的威胁模型。
- 实现最小权限、资源级授权、沙箱和高风险动作审批。
- 识别数据外泄、记忆污染、混淆代理和错误传播。
- 建立可重复的安全回归集和事件响应证据。

## 1. 主要威胁

| 威胁 | 例子 | 必要控制 |
|---|---|---|
| 直接提示注入 | 用户要求忽略规则、导出秘密 | 输入边界、最小权限、输出与工具策略 |
| 间接提示注入 | 网页/邮件指示 Agent 调用工具 | 外部内容视为数据、动作独立授权 |
| 工具滥用/越权 | 修改其他租户记录 | 资源级授权、专用身份、审计 |
| 数据外泄 | 将上下文发到攻击者 URL | 网络 egress 限制、字段过滤、DLP/审批 |
| 记忆污染 | 将恶意指令长期保存并跨会话使用 | 写入审查、来源、作用域、过期和删除 |
| 供应链风险 | 恶意 MCP server、Skill 或依赖 | 来源审查、锁定版本、哈希/签名、最小加载 |
| 过度自主 | 未审批付款、删除或公开发布 | 风险分级、人工审批、预算和终止 |
| 多 Agent 级联 | 不可信结果驱动另一个高权限 Agent | 跨 Agent 重新授权、schema 与信任边界 |

模型可以协助发现风险，但最终授权必须由确定性、可审计的代码和身份系统执行。

## 2. 分层防御

```text
1. 输入/内容：标记来源与信任级，不将外部文本升级为指令
2. 协议：严格 schema、大小限制、版本和异常处理
3. 身份：使用真实用户/服务身份，不信任模型传入身份
4. 授权：按动作、资源、租户、字段和环境逐项检查
5. 执行：沙箱、只读文件系统、资源限额、网络 egress allowlist
6. 审批：高风险动作展示具体参数和差异，批准对象不可替换
7. 输出：敏感信息检查、引用与结果验证、最小披露
8. 运维：预算、trace、审计、告警、撤销、删除与事件响应
```

每一层都可能失败，因此不能只依赖注入分类器或模型 guardrail。

## 3. 最小权限与混淆代理

Agent 平台持有高权限服务账号时，模型可能诱导它代替低权限用户执行动作，形成 confused deputy。防护要求：

- 将用户身份和授权上下文从可信会话传入，而非由模型生成。
- 在工具服务端重新检查“当前主体能否对该资源做该动作”。
- 读写工具分离，高权限操作使用独立短期凭据。
- 浏览不可信内容与访问秘密/写操作尽量分到不同信任域。
- 跨 Agent 委派不传递无限权限；子任务只获得必要 scope。

“先让模型判断这是否安全，再执行”不能代替真实授权。

## 4. 有意义的人工审批

审批界面至少展示：动作、资源、参数、数据去向、可逆性、预计副作用和关键差异。审批应绑定参数版本/哈希，并设置有效期。

不适合自动批准的场景：付款、删除、权限变更、生产发布、向外发送敏感信息。审批人疲劳也是真实风险；可通过降低高风险动作数量、批量展示独立低风险项和更清晰的预览改善，但不能把高风险项悄悄降为低风险。

拒绝、修改、超时和撤销都需要持久事件；被拒绝动作不应由 Agent 立即换个工具绕过。

## 5. 沙箱不是万能边界

沙箱需配合：非 root/低权限身份、只读或临时文件系统、资源与进程限制、受控网络、秘密隔离和短命环境。能执行任意 Python 的沙箱若同时挂载 Docker socket、云凭据和内网无限制访问，仍可能造成严重影响。

仅在本地脚本中过滤 `rm` 等字符串不是可靠安全机制。教学实验使用假工具和临时目录，不对真实系统执行攻击。

## 6. 最低实践：运行策略门与对抗回归

运行：

```bash
python code/ch14/policy_gate.py
```

完成：

1. 验证只读工具可在允许资源上执行。
2. 验证写工具需要审批，且审批只绑定具体参数。
3. 修改审批后的资源或金额，验证批准失效。
4. 模拟工具结果中的恶意指令，验证它不能直接提升权限。
5. 添加跨租户访问和未知工具测试。
6. 用 `templates/experiment-report.md` 记录拦截率、误报和漏报，不只记录攻击成功截图。

### 验收标准

策略门在模型之外独立测试；任何“模型说已经获批”都不能成为授权输入。所有测试使用模拟数据。

## 7. 安全评审清单

- [ ] 系统提示词中没有密钥、隐私数据或唯一安全规则。
- [ ] 工具服务端做真实身份与资源授权。
- [ ] 外部文档、网页、工具描述、记忆和其他 Agent 输出均不可信。
- [ ] 写操作有幂等、审计、取消和必要审批。
- [ ] 沙箱限制文件、进程、资源、网络与秘密。
- [ ] 记忆有作用域、来源、保留和删除。
- [ ] 评测包含注入、越权、外泄、重复与不可完成任务。
- [ ] 日志和 trace 有脱敏、访问控制与保留周期。

## 8. 本章自测

1. 在系统提示词写“禁止泄露数据”为什么不够？
2. 为什么用户说“我是管理员”不能改变工具权限？
3. 审批后参数发生变化，为什么必须重新审批？
4. 为什么多 Agent 架构可能扩大而不是缩小安全风险？

<details><summary>参考思路</summary>

1. 模型可能受注入或误判影响，密钥也不应进入提示词；需要模型外授权、隔离和输出控制。
2. 身份来自可信认证会话，而非自然语言声明；工具需独立校验。
3. 批准的是具体动作，参数变化可能改变资源、金额和数据去向。
4. 更多信任边界、凭据、状态和消息传播路径会带来级联与交接漏洞，需重新授权和审计。
</details>
