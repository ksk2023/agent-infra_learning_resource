# 第 12 章：Agent 评测与 Benchmark

## 本章导学

Agent 的输出只是轨迹的一部分。可靠评测要检查最终环境状态、关键过程约束、重复运行稳定性和成本。本章从私有任务集开始，再介绍公共 benchmark 的正确用法。

## 学习目标

- 建立单元、轨迹、端到端和线上四层评测。
- 区分 outcome、process、safety 与 efficiency 指标。
- 正确解释 pass@k 与 pass^k，避免一次成功偏差。
- 识别 judge、污染、环境漂移和评分器漏洞。

## 1. 评测金字塔

| 层 | 对象 | 示例 |
|---|---|---|
| 单元测试 | 解析器、工具、策略、评分器 | 非法参数被拒绝、幂等键生效 |
| 轨迹测试 | 一段固定模型/工具交互 | 工具结果回传、超时后不错误重试 |
| 端到端离线 | 完整任务与环境 | 修复测试通过、订单状态满足政策 |
| 线上评测 | 真实流量与业务目标 | SLO、人工接管、投诉、单位成功成本 |

下层测试定位快、成本低；上层更接近真实价值。不能用大量单元测试替代端到端，也不能只靠线上试验发现基本解析错误。

## 2. 先建自己的任务集

每条任务至少包含：

```text
task_id / 初始输入 / 环境快照
允许工具和数据作用域
成功判据 / 禁止副作用 / 政策约束
难度、能力标签、来源和版本
超时与预算
```

任务集应覆盖：

- 常见路径与困难长任务。
- 空结果、工具失败、信息不足与需要澄清。
- 越权、间接注入、重复请求和取消。
- 训练/调参未见过的保留集。

公开 benchmark 可用来比较通用能力，但业务发布门禁必须有私有、可复现、与真实风险对应的任务集。

## 3. 四类指标

| 类别 | 指标示例 | 注意 |
|---|---|---|
| Outcome | 最终状态成功率、正确率、引用支持率 | 优先可执行验证，不只读回答 |
| Process | 必要工具命中、非法动作、恢复、计划质量 | 过程好看不能弥补结果错误 |
| Safety | 策略违规、泄露、越权、审批覆盖 | 高风险违规不能被平均分掩盖 |
| Efficiency | 步数、token、P95、工具与人工成本 | 应报告单位成功任务成本 |

失败分类要互斥规则明确，例如 `model_format`、`tool_unavailable`、`permission_denied`、`verifier_failure`。若评分器本身失败，不应直接记为 Agent 任务失败。

## 4. pass@k 与 pass^k

设同一任务独立重复 `k` 次，单次成功概率为 `p`，仅作简化模型：

```text
pass@k = 1 - (1 - p)^k   # k 次中至少一次成功
pass^k = p^k             # k 次全部成功
```

- `pass@k` 适合“可以生成多个候选并选择/验证一个”的场景。
- `pass^k` 更关注每次都可靠的稳定性。
- 两者都不能从不独立的一次试验直接精确估计；实际应运行多次并报告原始成功序列和置信区间。
- 如果系统能自动选候选，选择器本身也必须计入成本与成功率。

## 5. LLM-as-a-Judge 的边界

模型评审适合难以完全规则化的语义维度，但需：

- 用人工标注集校准准确性、偏差和一致性。
- 固定 judge 模型、prompt、输入顺序和评分 rubric。
- 对成对比较做位置交换，检查位置偏差。
- 防止被评答案中的指令操控 judge。
- 保存评审证据与原始分数，不只保存聚合平均。

涉及资金、权限、安全和事实正确性的关键结论，优先使用确定性检查与人工抽查。

## 6. 公共 Benchmark 怎么选

| Benchmark | 主要任务 | 学习点 |
|---|---|---|
| AgentBench | 多类交互环境 | 跨环境能力与失败分析 |
| GAIA | 通用助手、浏览、工具、多模态 | 通用任务，不等于特定业务可靠性 |
| SWE-bench | 真实 GitHub issue 与测试 | 代码修复的可执行结果验证 |
| WebArena | 自托管网站任务 | 可复现 Web 环境与状态检查 |
| OSWorld | 真实操作系统与应用 | 多模态 computer-use 与环境初始化 |
| τ 系列 benchmark | 工具—Agent—用户交互与政策 | 动态对话、工具结果、业务约束和重复试验 |

版本、数据子集、harness、工具和模型差异会破坏分数可比性。不要把不同榜单或不同版本的数字拼成统一排名。

## 7. 最低实践：计算并解释可靠性

运行：

```bash
python code/ch12/eval_metrics.py
```

完成：

1. 对同一任务输入多次成功/失败结果，计算单次成功率与 pass^k。
2. 比较两个总成功率相同但稳定性不同的 Agent。
3. 加入一个安全违规任务，说明为何平均成功率不能掩盖它。
4. 将一条评分器错误标记为 `invalid`，避免混入 Agent 失败率。
5. 用 `templates/eval-task.md` 写 5 条自己的任务定义。

### 验收标准

报告同时给出分子/分母、重复次数、无效样本处理和原始记录位置，而不只给一个百分数。

## 8. 本章自测

1. pass@8 很高能否证明用户每次请求都很可靠？
2. 为什么最终文本 judge 不能替代环境状态检查？
3. 为什么评分器故障要与 Agent 失败分开？
4. 公共 benchmark 分数高能否直接作为生产上线依据？

<details><summary>参考思路</summary>

1. 不能，它描述至少一次成功；单次服务可靠性更接近单次成功率或 pass^k。
2. 文本可能声称完成但状态未改变或政策被违反，环境检查更接近真实结果。
3. 否则会把评测基础设施问题错误归因于 Agent，破坏优化方向。
4. 不能，还需真实业务任务、私有保留集、安全、SLO 和线上验证。
