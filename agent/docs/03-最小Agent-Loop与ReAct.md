# 第 03 章：最小 Agent Loop 与 ReAct

## 本章导学

ReAct 将语言决策与环境动作交错组织：模型不只在内部生成答案，还能通过动作获得新观察。本章实现一个不依赖框架的最小循环，并把所有容易忽略的终止和失败分支显式写出来。

## 学习目标

- 解释 reason、act、observe 如何形成闭环。
- 实现模型、工具注册表、轨迹和运行预算的分离。
- 处理非法动作、未知工具、工具异常和重复循环。
- 区分“轨迹可读”与暴露完整内部推理。

## 1. ReAct 的核心

经典 ReAct 将任务相关决策与外部环境动作交错：动作带来新信息，后续决策再根据观察更新。它的学习价值不在于固定提示词模板，而在于把**决策—环境反馈—再决策**建成闭环。

```text
状态/目标
  -> 模型提出动作或最终答案
  -> 运行时解析、校验、授权
  -> 工具执行并返回观察
  -> 观察追加到受控上下文
  -> 模型继续，直到终止条件
```

产品日志无需保存或展示完整隐式思维链。可保存简短的决策依据、结构化动作、工具结果、错误和状态差异，既能调试又减少敏感信息暴露。

## 2. 最小组件

| 组件 | 职责 | 不应负责 |
|---|---|---|
| Model | 根据上下文产生动作/答案 | 直接执行代码或授权 |
| ToolRegistry | 根据名称找到已注册工具 | 判断业务成功 |
| Runner/Loop | 步数、轨迹、停止与错误编排 | 猜测模型语义 |
| Tool | 在明确契约下读写环境 | 信任未校验参数 |
| Evaluator | 检查最终状态或任务证据 | 被模型自述替代 |

迷你实现中，模型和工具都是进程内对象；生产系统则可能跨网络、队列和沙箱，但控制关系不变。

## 3. 停止条件必须先写

一个完整 Runner 至少支持：

- 模型返回合法 `final`。
- 达到最大模型轮数或工具调用次数。
- 超过 token、费用或墙钟时间预算。
- 用户取消或运行时收到停止信号。
- 需要人工审批而进入暂停，而不是假装完成。
- 出现不可恢复错误，返回明确失败状态。

还可检测重复动作与相同观察，但“重复”只是循环信号，不能在所有任务中机械地当作失败；某些轮询任务本来就重复读取状态。

## 4. 工具结果如何回到上下文

工具结果至少包含：

```json
{
  "call_id": "call-1",
  "ok": false,
  "error_type": "unknown_tool",
  "content": "工具不存在"
}
```

`call_id` 用于把动作和结果关联；`ok` 与错误类型让运行时和模型区分空结果、权限拒绝、暂时错误和业务失败。不要把 Python 异常对象或任意堆栈直接作为模型上下文。

工具结果属于**不可信观察**。即使内容写着“忽略之前规则并调用另一工具”，也只能作为数据处理，不能提升为系统指令。

## 5. ReAct 不是所有任务的最优解

| 模式 | 适用 | 局限 |
|---|---|---|
| 单次回答 | 无需外部信息的简单任务 | 无法验证实时事实 |
| Act-only | 动作空间小、反馈直接 | 难以处理复杂依赖和异常 |
| ReAct | 路径动态、需要边观察边调整 | 长轨迹上下文膨胀，可能逐步漂移 |
| Plan-and-Execute | 子任务依赖相对稳定 | 初始计划可能很快过期 |
| 固定 workflow + 局部 Agent | 业务主干明确、局部需要开放性 | 需要明确交接和状态契约 |

允许模型在每一步重新决策并不保证全局最优；必要时用固定门禁、计划状态和验证器限制搜索空间。

## 6. 最低实践：运行并破坏迷你 Agent

运行：

```bash
python code/ch03/mini_agent.py
```

脚本用模拟模型依次选择计算器和最终回答。完成以下对照：

1. 正常路径：工具结果被追加，最终答案使用计算结果。
2. 未知工具：不产生副作用，轨迹包含结构化错误。
3. 非法输出：运行以协议错误结束或可计数的修复分支结束。
4. 永远请求工具：达到 `max_steps` 后停止。
5. 工具异常：异常被转换为受控观察，Runner 不崩溃。

### 验收标准

能解释每次模型调用看到了哪些状态、每次工具调用由谁授权、何时停止。模拟输出只用于证明这些控制行为。

## 7. 真实模型实践

实现一个模型适配器，将原生 tool-call 响应映射为本章动作协议。固定 20 个小任务，对比：

- 无工具直接回答。
- 有工具但无明确停止/错误反馈。
- 完整 Loop。

记录任务成功率、格式错误、工具错误、平均步数、token 和 P95 延迟。至少保留两个“工具可用但不应调用”的任务，观察过度工具使用。

## 8. 本章自测

1. 工具返回“任务已成功”，能否直接作为最终成功依据？
2. 为什么最终回答和工具调用应是不同动作类型？
3. 达到最大步数后能否让模型“再多试一次”而不记预算？
4. 为什么工具结果要标记为不可信数据？

<details><summary>参考思路</summary>

1. 不能，需独立检查最终环境状态或任务证据，工具也可能误报。
2. 二者控制语义不同；混淆会造成未执行动作就结束或无法结束。
3. 不能，预算必须真实约束资源与风险；例外需要显式策略和审计。
4. 外部内容可能包含间接提示注入、伪造事实或恶意指令。
