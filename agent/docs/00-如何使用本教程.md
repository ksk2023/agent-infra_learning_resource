# 第 00 章：如何使用本教程

## 本章导学

Agent 横跨大模型、软件工程、检索、分布式状态、安全与人机交互。最危险的学习方式是先追逐所有框架，再补基础。本章帮你建立够用的起点，并用可验证产出驱动后续学习。

## 学习目标

完成本章后，你应该能够：

1. 判断自己的起点与目标方向。
2. 建立隔离、可复现且不泄露密钥的实验环境。
3. 区分“跑通 Demo”“理解机制”“证明可靠”。
4. 创建第一份学习笔记、实验报告与评测任务。

## 1. 前置知识检查

不要求全部精通，但遇到缺口要回补：

| 领域 | 最低要求 | 自检问题 |
|---|---|---|
| Python | 函数、类、dataclass、异常、虚拟环境、测试 | 能否给一个 JSON 解析器写边界测试？ |
| Web 基础 | HTTP、JSON、REST、超时、状态码 | 能否区分客户端重试与重复执行副作用？ |
| LLM 基础 | token、上下文窗口、temperature、系统指令 | 能否解释模型输出为什么不是数据库事实？ |
| 数据结构 | 列表、字典、队列、图、基本复杂度 | 能否检查任务依赖中是否有环？ |
| 系统基础 | 进程、文件权限、环境变量、日志 | 能否限制工具只读一个目录？ |
| 实验基础 | 对照组、分位数、成功率、可复现性 | 一次成功能否代表稳定能力？ |

模型原理可按需阅读 [Datawhale Happy-LLM](https://github.com/datawhalechina/happy-llm)；计算机基础可使用 [CS 自学指南](https://github.com/PKUFlyingPig/cs-self-learning)。它们不是本教程的依赖。

## 2. 环境原则

### 2.1 一个项目一个环境

不要把所有 Agent、模型和向量数据库框架装进同一个全局环境。先跑标准库实验，再按具体章节创建隔离环境并锁定依赖。

```bash
python -m venv .venv
# Linux/macOS
source .venv/bin/activate
# Windows PowerShell
# .venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
```

建议记录 Python、框架、模型提供方、模型标识、工具版本和运行参数。密钥通过环境变量或密钥管理工具注入；`.env` 不应进入 Git，trace 默认不记录完整敏感内容。

### 2.2 先离线，再接真实模型

最小验证顺序：

```text
标准库测试 -> 模拟模型轨迹 -> 假工具/沙箱工具
  -> 真实只读 API -> 小规模任务集 -> 受限写操作 -> 生产评审
```

模拟模型是测试替身，可精确触发非法 JSON、未知工具、重复动作和超时等分支。它不能模拟真实模型的推理质量。接真实模型时先用只读工具和小任务，不要直接赋予付款、删库或公开发布权限。

## 3. 本教程的四种任务

| 标记 | 目的 | 是否需要模型 API |
|---|---|---|
| 概念练习 | 画图、推导、比较方案 | 否 |
| 最低实践 | 运行离线实验并留下证据 | 否 |
| 真实模型实践 | 测量模型、提示词和工具的组合效果 | 是 |
| 源码任务 | 从具体问题进入真实项目调用链 | 视项目而定 |

每章资源分为：

- **主干**：直接对应当前机制，优先学。
- **进阶**：需要更多前置知识、算力或环境。
- **索引**：用于查资料，不要求从头阅读。

## 4. 如何做一次可信 Agent 实验

一个最小可信实验至少包含：

1. **任务分布**：任务来自哪里，是否覆盖常见、困难、对抗和不可完成任务。
2. **成功标准**：优先检查最终环境状态或执行结果，不只评价文字像不像。
3. **固定条件**：模型、提示词、工具、数据快照、依赖、参数、预算和版本。
4. **变量**：一次只改变一个主要因素，例如是否启用检索。
5. **重复运行**：非确定性系统不能只运行一次；记录每次轨迹和失败。
6. **效率与风险**：除了成功率，还记录步骤、token、延迟、工具成本与策略违规。
7. **原始证据**：保存 JSON/JSONL、环境检查结果和评分器版本，而非只保存截图。
8. **限制**：样本量、数据泄漏、judge 偏差、环境漂移和未覆盖场景。

推荐流程：

```text
定义任务 -> 建确定性基线 -> 小集冒烟 -> 重复实验
  -> 失败分类 -> 改一个变量 -> 回归 -> 解释边界
```

## 5. 最低实践：建立学习基线

创建 `notes/baseline.md`，回答：

- 我的目标岗位或问题是什么？
- 我每周可投入多少小时，是否有模型 API 或 GPU？
- 我能否独立实现 JSON 解析、HTTP 调用和单元测试？
- 我是否做过带对照组的实验，而不是只运行 Demo？
- 16 周后我要展示哪一个可复现项目？

再复制 `templates/experiment-report.md`，用任意离线实验走一遍报告流程。实验的“结果”应包括测试输出和限制，而不是只写“运行成功”。

## 6. 本章自测

1. 为什么模拟模型适合测试 Agent Loop，却不能用于证明真实任务成功率？
2. 为什么“回答看起来很合理”不足以证明工具任务完成？
3. 一个实验同时更换模型和工具，成功率提高 10%，能否归因于新工具？
4. 为什么 API key 不应出现在系统提示词或完整 trace 中？

<details><summary>参考思路</summary>

1. 模拟模型只提供预定动作，能验证控制流，不包含真实模型的能力与失败分布。
2. 应检查环境状态、工具结果或业务约束；语言可能掩盖未执行或错误执行。
3. 不能，需要控制变量，分别隔离模型与工具的影响。
4. 提示词和日志可能被模型、外部服务或更多运维人员看到，应使用密钥管理并做脱敏。
</details>
