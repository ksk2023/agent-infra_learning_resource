# 阶段项目

四个项目共享一条原则：**先定义问题和正确性，再测量，最后优化**。没有硬件时提交设计、模拟和可运行 CPU 代码，但明确标注哪些结论尚未实测。

## P1：单机性能分析报告

### 目标

对一个小模型或关键算子建立从理论估算到 profile 的分析闭环。

### 必做

1. 固定模型、shape、dtype 和软件环境。
2. 用第 03、05 章脚本估算 roofline 或训练显存。
3. 在 GPU 上做 profiler；无 GPU 时仅提交估算与实验方案。
4. 选择一个变量做对照，例如 micro-batch、checkpointing 或 dtype。
5. 报告绝对结果、相对变化、质量/数值正确性和反例。

### 验收

- 理论与实测差异有解释，不用“可能比较复杂”敷衍。
- 能指出当前最大瓶颈及下一项最有区分度的实验。

## P2：可恢复分布式训练

### 目标

用极小模型理解 DDP/分片、扩展效率和 checkpoint 恢复。

### 必做

1. 正确切分数据并验证多进程更新一致。
2. 比较单进程与多进程吞吐，计算 scaling efficiency。
3. 条件允许时比较 DDP 与 FSDP/ZeRO 的显存和通信。
4. 保存完整训练状态，在非保存期与保存期分别做一次测试故障。
5. 记录恢复点、损失步数、恢复时间和数据位置。

### 验收

- 不用 CPU/Gloo 结果推断 GPU/NCCL 性能。
- 恢复后 optimizer、step、数据游标和模型状态经过检查。

## P3：Mini 推理调度器与真实引擎 Benchmark

### 目标

把调度逻辑和真实 serving 测量分开学习，再建立对应关系。

### 必做

1. 扩展 `code/ch10/batching_simulator.py`，增加到达过程或优先级。
2. 为请求生命周期、容量和完成行为写单元测试。
3. 推导一个模型的 KV Cache 容量。
4. 在 vLLM 或 SGLang 上固定 workload 扫描并发。
5. 输出 TTFT/TPOT/E2E 分位数、吞吐、错误率、显存和原始数据。

### 扩展

Prefix cache、量化或 speculative decoding 只选择一个变量做对照。

### 验收

- 区分模拟调度结论与真实 GPU 性能结论。
- 至少解释一个吞吐提升但 SLO 变差的点。

## P4：可观测、可回滚的 LLM 服务

### 目标

将推理引擎包装为具备容量、SLO 和发布管理的测试服务。

### 必做

1. 定义流量模型和 TTFT/TPOT/成功率 SLO。
2. 提供 readiness、优雅退出、队列和限流。
3. 建立用户、引擎、资源三层指标与告警。
4. 设计并演练一次灰度、一次回滚和一次实例故障。
5. 计算指定负载下的单位有效请求/token 成本。

### 验收

- 告警有响应 runbook，发布绑定模型与引擎版本。
- 故障演练仅在自有测试环境进行，日志不包含密钥或敏感内容。

## 评分量规（每项 0–2 分）

| 维度 | 0 | 1 | 2 |
|---|---|---|---|
| 正确性 | 无法验证 | 有少量测试 | 多场景测试与回归 |
| 可复现 | 只有截图 | 有命令和部分配置 | 干净环境可复现、原始数据齐全 |
| 分析 | 只报结果 | 有简单解释 | 有对照、反例、边界与下一步 |
| 工程 | 单脚本难维护 | 基本结构清晰 | 文档、测试、版本和安全完整 |
| 迁移 | 只会复刻 | 能改参数 | 能为新负载重新设计并验证 |

8 分以下继续补证据，不以项目数量代替深度。
